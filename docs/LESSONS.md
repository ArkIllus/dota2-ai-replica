# 经验总结

## 1. 先把“复刻”拆成可以验收的目标

视觉相似、操作相似、规则一致、脱离原客户端运行，是不同的要求。早期没有把它们拆开，导致能运行的原型与使用者期待发生偏差。后续应为每项分别写出验收场景，再选择引擎和实现路线。

## 2. 资料的可信范围要跟着结论走

KV 数值只能证明配置内容；反编译只能提供相应函数的局部证据；局部原码比较只能证明选定输入和范围内的一致性。REA 提高了收集和组织证据的效率，但不会自动把局部结论扩大为完整机制。

## 3. 把纯规则与引擎适配分开

纯 Lua 核心让战斗状态可以在 Python + Lupa 中快速回放。引擎适配负责玩家绑定、输入、位置、模型与 HUD。发生问题时，先判断是核心结算错误，还是原生实体与核心状态没有同步，而不是混在一处反复修改。

## 4. 不要让两套系统同时拥有结算权

在已有游戏里替换玩法，最隐蔽的问题是原版伤害、自动兵线、购买或状态仍在工作。明确哪些原生行为保留，哪些要拦截，才能避免双重伤害、库存分叉等现象。当前实现仍需要继续核验这一边界。

## 5. 按验证层级报告结果

| 验证 | 能说明什么 | 不能替代什么 |
| --- | --- | --- |
| Lua 场景测试 | 选定输入下的核心规则 | Source 2 实体、网络和界面行为 |
| 引擎订单与断言 | 适配层在游戏中的有限结果 | 真人鼠标键盘路径 |
| 实际操作与日志 | 某次输入到结果确实打通 | 全部技能、分辨率和版本兼容 |
| 原版与重实现对照 | 同条件下选定行为的一致性 | 未测规则、其他版本或完整对局 |

## 6. 错误要可定位，未知就保留未知

必填配置缺失应明确报错；不能静默跳过再宣称“没有崩溃”。同时，时序相关不等于因果已证实：变身崩溃的规避方式可以记录，未经证明的引擎根因不应写成事实。

## 7. 不要把开发机当作运行条件

写死游戏路径、从旧项目导入依赖、强制低分辨率，都会让“本机可用”变成别人的障碍。发布时应提供明确参数、独立依赖和可执行命令；保留用户原生设置，并从仅包含发布文件的目录再次运行测试。

## 8. AI 的贡献与原版的贡献都应写明

AI 编写适配代码并不意味着引擎和美术也是 AI 产出。使用原版数值，也不意味着完整技能代码由原作提供。清楚标注实现归属，是评价这次实验的前提。
